Registration Campaigns for Passkeys and Microsoft Authenticator

Foundations

Overview & prerequisites

A registration campaign nudges users to set up a passkey or Microsoft Authenticator during sign-in. When a user performs an interactive sign-in with multifactor authentication (MFA)—a sign-in requiring two or more verification factors—they can be prompted to set up the targeted method. Admins include or exclude users or groups to control who is nudged, creating targeted campaigns that move users off less secure methods.

The two supported methods (click a card to flip)

Key ruleA campaign targets one authentication method at a time.

Prerequisites by campaign

Targets users who don't already have Authenticator push notifications set up.

  • Enable users for Authenticator in the authentication methods policy (the tenant policy that controls which methods users may use).
  • Authentication mode must be Any or Push. In Passwordless mode, users aren't eligible (related: Enable passwordless sign-in with Authenticator).
  • Targeted users must also be in scope for the method.
  • Enable the passkey (FIDO2) method in the authentication methods policy (related: Enable passkeys).
  • Enable Allow self-service setup in the passkey (FIDO2) method configuration.
  • Targeted users must also be in scope for the method.
Optional first stepBefore configuring, check how many users already registered each method in the Authentication methods activity report.
Mechanics

How a registration campaign works

The campaign prompts users to set up a stronger method after they complete MFA. The MFA requirement depends on the campaign state and the targeted method.

Interactive sign-in→ Completes MFA→ Conditional Access for security-info registration applies→ Eligible? → nudge

MFA requirement explorer

Campaign stateTargeted methodMFA requirement
Microsoft managedMicrosoft AuthenticatorUser completes MFA by SMS or voice call
Microsoft managedPasskey (FIDO2)Any method
EnabledMicrosoft AuthenticatorAny method
EnabledPasskey (FIDO2)Any method

For either campaign, a user is prompted only if they're eligible; eligibility depends on the state and the targeted method.

Note: Conditional Access applies before the nudge

During regular sign-in, Conditional Access policies (Entra's if-then access rules) that govern security information registration apply before the nudge. Example: if a policy allows security-info updates only from an internal network, users aren't prompted unless they're on that network.

Configuration model

Choose a campaign state

The campaign state determines who configures and manages the campaign settings.

Microsoft selects the targeted method and settings and updates them to match current best practices. You define which users are included. Use it to apply Microsoft's recommended settings.

You select the targeted method, snooze settings, and included users. Use it when you need to control the targeted method or snooze behavior, or to run a passkey campaign for users whose passkey profile isn't eligible under Microsoft managed.

The registration campaign is disabled.

Settings & eligibility Microsoft applies

Days allowed to snooze: 1 · Limited snoozes: Enabled — after 3 snoozes, registration is required.

Eligible users meet all of:

  • Perform MFA by voice call or text message (SMS)
  • Are enabled for Authenticator push notifications in the authentication methods policy
  • Don't already have Authenticator push set up

Days allowed to snooze: 1 · Limited snoozes: Disabled — unlimited snoozes.

Eligible users meet all of:

  • Sign in by using any MFA method
  • Are in at least one eligible passkey profile (below)

Passkey profile eligibility for Microsoft managed

A passkey profile is a passkey (FIDO2) method configuration scoped to users, which can restrict passkey types or providers. In the managed state with a passkey target, each scoped user's profile is checked at sign-in. A user is nudged if they're in at least one profile meeting these criteria. This check doesn't apply in the Enabled state.

Profile configurationDetails
UnrestrictedNo passkey profile restrictions
Synced-onlySynced passkeys only; no key restrictions
Device-bound-onlyDevice-bound passkeys only; no key restrictions
AAGUID-restrictedAllow list contains at least one AAGUID for: iCloud Keychain · Google Password Manager (GPM) · Microsoft Authenticator passkey · Microsoft Entra passkey on Windows
Device-bound with attestation enforcedKey restrictions aren't evaluated

AAGUID = Authenticator Attestation GUID, an identifier for the passkey provider/model.

Eligibility checker

AAGUIDs on the allow list

AAGUID-restricted profile rules
  • You can add other AAGUIDs, as long as the allow list contains at least one AAGUID for a listed provider.
  • Exclude and Block lists are ignored for campaign eligibility. Entries may exist there, but targeting logic doesn't evaluate them.
  • iCloud Keychain or GPM AAGUIDs → select the Synced passkey profile type. Authenticator passkey or Entra passkey on Windows AAGUIDs → select Device bound. A mix → select both types.
Note: one eligible profile is enough

If a user is in multiple passkey profiles and any one meets the criteria, the user is eligible.

User choice

Snooze experience

A user can postpone setup by selecting Skip for now. After the snooze duration elapses, they're prompted again the next time they sign in and perform MFA.

Setting (Enabled state)Description
Days allowed to snoozePeriod between successive prompts. With 3 days, users who skip aren't prompted again for 3 days.
Limited number of snoozesEnabled: skip 3 times, then must register. Disabled: unlimited snoozes.
NoteWith limited snoozes enabled, the snooze count is tracked per user and persists across campaign restarts and configuration changes, including targeted-method updates.

User experience

  1. Complete MFA.
  2. Prompt appears if you're enabled for Authenticator push and it isn't set up, to improve your sign-in experience. Other features—passwordless sign-in, self-service password reset, or security defaults—might also prompt you to set up a method.
  3. Select Next and step through Authenticator setup.
  4. Or select Skip for now to snooze for the number of days your admin configured. Users with free and trial subscriptions can snooze up to three times.
  1. Complete MFA.
  2. Prompt appears if passkey registration is enabled for your account and a qualifying passkey isn't available for your current platform. The evaluation is per device-and-browser combination, not what's registered on your account (see Passkey nudge evaluation).
  3. Select Next. Your device or browser shows the passkey creation prompt and where it will be saved; depending on platform, you may pick a different provider or save location.
  4. Verify identity with face, fingerprint, or PIN. The passkey is saved.
  5. "Let's name your passkey": enter an identifying name, then Next.
  6. "Passkey created": select Done to finish signing in.
  7. Or select Skip for now to snooze the prompt.
  8. Registration error? An error screen offers Skip. These skips don't count toward the limited snooze count, so errors don't block sign-in.
Admin task

Enable the campaign in the Microsoft Entra admin center

Steps
  1. Sign in as at least an Authentication Policy Administrator.
  2. Browse to Entra ID > Authentication methods > Registration campaign, select Edit.
  3. Choose State: Enabled (configure method, snooze duration, snooze limit, targets) or Microsoft managed (method, duration, limit set automatically and not configurable; targets still configurable — related: Protecting authentication methods in Microsoft Entra ID).
  4. Choose Authentication method: Microsoft Authenticator, or Passkey (a passkey meeting at least one profile the user is scoped to).
  5. Select users or groups to include/exclude, then Save.

Passkey logic

How passkey registration nudges are evaluated

Once a user meets eligibility, their passkey profile decides whether existing passkeys suppress the nudge across all platforms or only for the current OS-and-browser combination (platform). These rules apply in both Enabled and Microsoft managed states, and are separate from managed-state profile eligibility (see Microsoft managed state): managed nudges only users in an eligible profile; Enabled nudges any passkey-enabled user regardless of profile.

Step 1 — How the profile affects the nudge

When is the nudge suppressed?
UnrestrictedYesUser has a qualifying credential for the current OS + browser (see platform table)
Synced-onlyYesUser has a qualifying local synced passkey for the current platform; otherwise nudged where a compatible synced passkey can be registered
Device-bound-onlyYesUser has a qualifying local device-bound passkey for the current platform; otherwise nudged where a compatible device-bound passkey can be registered
AAGUID-restrictedNoAfter one eligible passkey is registered, suppressed across all OS + browser combinations
Device-bound with attestation enforcedNoAfter one eligible passkey is registered, suppressed across all OS + browser combinations
NotesAn eligible passkey must meet the profile's requirements; a non-conforming passkey doesn't suppress the nudge. Windows Hello for Business (WHfB, Windows' built-in device-bound credential) registration doesn't follow passkey profile restrictions—e.g., a synced-only user can still register WHfB.

Step 2 — Platform table (pick a platform to highlight)

For unrestricted, synced-only, and device-bound-only profiles, a passkey on the account doesn't necessarily suppress the nudge everywhere—it must qualify under the profile and the platform rule.

✓ suppresses the platform-specific nudge (subject to profile requirements). — doesn't suppress under this rule; it says nothing about whether the credential can authenticate there. Linux users aren't nudged by passkey campaigns.

Enable the campaign by using Graph Explorer

You can also configure the policy with Microsoft Graph (Microsoft's REST API) via Graph Explorer, using the authentication methods policy APIs. Requires at least Authentication Policy Administrator.

  1. Sign in to Graph Explorer and consent to Policy.Read.All and Policy.ReadWrite.AuthenticationMethod.
  2. Retrieve the policy: GET https://graph.microsoft.com/v1.0/policies/authenticationmethodspolicy
  3. Update registrationEnforcement → authenticationMethodsRegistrationCampaign with a PATCH that contains only the updated registrationEnforcement section: PATCH https://graph.microsoft.com/v1.0/policies/authenticationmethodspolicy

Edge cases

Frequently asked questions




  
  
  
  





What's the difference between the Enabled and Microsoft managed states?
Enabled: you configure method, snooze duration, snooze limit, and targets. Microsoft managed: Microsoft sets method, duration, and limit from best practices and keeps them current. Targets are configurable in both. See also: Campaign states.


Why isn't a scoped user nudged for passkeys under Microsoft managed?
They must be in at least one eligible passkey profile. If their only profiles don't qualify—e.g., an AAGUID-restricted profile whose allow list has no supported AAGUID—they aren't nudged. Enabled state doesn't apply these checks.


Can users be nudged within an application?
Yes—embedded browser views in certain applications are supported. Not in out-of-the-box experiences (OOBE) or browser views embedded in Windows Settings.


Can users be nudged within an SSO session?
Yes, during interactive sign-ins that satisfy MFA, if other eligibility is met. Silent single sign-on (SSO) events without user interaction, such as refresh token redemption, don't display nudges.


Can users be nudged on a mobile device?
Authenticator campaigns: not supported on mobile. Passkey campaigns: supported in mobile browser experiences and native iOS apps; native Android app support isn't currently available.


How long does the campaign run?
As long as you want. Disable it in the admin center or via APIs when finished.


Can each group of users have a different snooze duration?
No. Snooze duration is a tenant-wide setting for all groups in scope.


What if I don't want users to be able to skip registration?
In the Enabled state, set Days allowed to snooze to 0 and Limited number of snoozes to Enabled. Users can still snooze up to three times but are prompted on every MFA; after the third snooze, registration is required.


Can users be nudged to set up passwordless phone sign-in?
No. Only Authenticator (MFA) or passkey registration are targetable.


Does a user who signs in with a non-Microsoft authenticator app see the nudge?
Depends on the target. A passkey campaign can nudge after MFA with a non-Microsoft app if other requirements are met. An Authenticator campaign prompts only after MFA by SMS or voice call.


Does a user with Authenticator set up only for TOTP codes see the nudge?
They're eligible for an Authenticator campaign if push isn't set up, but the prompt appears only after MFA by SMS or voice—not after using a time-based one-time password (TOTP) code.


Does a user who already has a passkey see the nudge?
The nudge checks for a local passkey for the current OS + browser. If present, no nudge—so a user may be nudged on one device but not another. See also: Passkey nudge evaluation.


Can I run campaigns for both Authenticator and passkeys at the same time?
No. One targeted method at a time per tenant.


If a user just went through MFA registration, are they nudged in the same session?
No. For a good experience, users aren't nudged to set up Authenticator in the same session in which they registered other methods.


Can I nudge users to register another authentication method?
Yes—Authenticator or passkey (FIDO2). Choose the target when configuring.


Can I hide the snooze option and require setup?
Not immediately. Enable Limited number of snoozes so users can postpone up to three times, after which setup is required.


Can I nudge users if I'm not using Microsoft Entra MFA?
No. The nudge works only for users doing MFA with Microsoft Entra MFA.


Are guest users nudged?
Yes for Authenticator campaigns; no for passkey campaigns, because passkey support for guests isn't currently available.


What if the user closes the browser?
Same as snoozing. If setup is required after three snoozes, they're nudged at next sign-in.


Why don't some users see a nudge with a Conditional Access policy for "Register security information"?
No nudge if the user is in scope for a policy that blocks access to the Register security information page.


Do users see a nudge when a terms-of-use screen appears?
No.


Do users see a nudge when Conditional Access custom controls apply?
No—not if the user is redirected during sign-in by custom controls.
